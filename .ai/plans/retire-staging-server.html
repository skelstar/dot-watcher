Retire the Staging server

Branch retire-staging-server · plan written 2026-11-06 · status: proposed, nothing executed · replaces the earlier per-environment-database plan

Decision: there is no Staging server on Tatooine. The staging branch stays as the integration branch and is exercised locally against the Docker Postgres in docker-compose.yml. TestFlight builds move to the Production server. A release is a merge of staging into main; Kraken (the Tatooine deploy app) then offers it to deploy to Production.

1. Where this ends up

Now
PR → staging branch
Staging pod (ns dot-watcher-server-staging) ← TestFlight
Promote PR → main, /deploy builds :latest
One shared Postgres database, used by both pods
After
PR → staging branch, tested locally (Docker Postgres)
Promote PR → main → Actions builds images, publishes a GitHub Release
Kraken: press Deploy → Production pod ← TestFlight, App Store
One Postgres database, Production only

2. What this removes from the earlier plan

  • No second database, role, or data split. There is only one environment with a server, so the database question disappears. Production keeps dotwatcher untouched.
  • Your own data carries over. The iPhone/TestFlight account and sessions already live in that shared database (merged in the 2026-07-22 cutover), so moving TestFlight to Production needs no data copy and no re-registering.
  • The "TestFlight can't join Production sessions" concern is gone. It was only a problem if the databases were split.

3. Constraints from Kraken

  • Kraken only reads GitHub Releases from the app repo. It never looks at branches, so the branch model is ours to keep: PRs to staging, promote to main, enforce-staging.yml unchanged.
  • A release is a published GitHub Release tagged vX.Y.Z with a release.json asset: project, version (equal to the tag), commit, images for each of server and client pinned by digest (ghcr.io/skelstar/dot-watcher-server@sha256:…), and migrations. Anything else is skipped.
  • Production-only projects are supported. The release is offered straight to Production, with a warning that nothing was tested first. That is the case here, since testing happens locally.
  • Rollback swaps images only. Schema changes must stay additive so the previous release still starts (SessionStore.Initialize() already works this way).
  • Kraken's tag pattern is hardcoded to ^v\d+\.\d+\.\d+$. This repo already has mobile tags v1.0.0–v1.3.0 and android-v0.2.x, so server releases need their own tag space (step 3).
Order matters. Installed TestFlight builds point at the Staging hostname. Do not remove the Staging server until a TestFlight build pointing at Production is out and the testers (you) have it installed, or the installed app stops working. Production must also be running the new server code before that build ships.

4. Plan

Tags: repo changes in this repository, config changes in Tatooine-Configuration (Kraken and Flux), tatooine commands on the cluster, run by you.

  1. Inventory the live wiring. tatooine
    Read-only. For the two Production Deployments (dot-watcher-server, dot-watcher-client): the Flux Kustomization that owns each, how ConnectionString reaches the pod (a hand-patched secretKeyRef, per the cutover notes), the image currently running, and whether ghcr-pull-secret exists in each namespace. The Production namespaces stay as they are, so no PVC moves or data copy is needed.
  2. Back up the database. tatooine
    pg_dump -Fc dotwatcher from the Postgres pod to a file off the node, and prove it restores into a scratch database. There is no backup today, and everything below ends with Production being the only copy.
  3. Release workflow for dot-watcher. repo
    New .github/workflows/release.yml, triggered by a push to main (so the promote PR merge is the release). It should:
    • build and push ghcr.io/skelstar/dot-watcher-server and dot-watcher-client (the client needs the LINZ key as a build argument; the build fails without it);
    • write release.json with both digests, the commit, and migrations set when server/Stores/SessionStore*.cs changed since the previous release (dot-watcher has no migrations folder, so the schema file is the signal);
    • publish the GitHub Release using the server tag prefix from the next item, with generated notes.
    Model it on tatooine-deploy/.github/workflows/release.yml and activity-logger's. Version numbers must not clash with the mobile app tags.
  4. Server tag prefix in Kraken. config
    Small change in the Kraken repo: an optional tagPrefix per project in projects.yaml (for example server-v) replacing the hardcoded v in src/real/github.ts, so mobile tags are ignored and server releases get their own numbers. Separate PR in that repo.
  5. Declare the Production deployment. config
    In Tatooine-Configuration, give deployments/dot-watcher-server and dot-watcher-client a kustomization.yaml that lists their manifests and pins the image by digest (the same approach as activity-logger's existing production-only folder). Put the ConnectionString secretKeyRef env in the manifest so a redeploy can't lose it (the problem recorded in the old cutover plan). Add the Production-only dot-watcher entry to Kraken's projects.yaml. Remove the dead DbPath and the stale hostname from server/.deploy.yaml, or delete that file once /deploy is retired.
  6. First Kraken release and deploy of Production. tatooine
    Promote staging to main (it is 7 commits ahead of main today), let the release workflow run, then deploy it to Production from Kraken. Production must run the code the TestFlight build expects before step 7.
  7. Move TestFlight to Production. repo
    In the iOS app, remove the TestFlight → Staging routing in LocationManager.swift (the isTestFlightBuild branch that selects DotWatcherStagingAPIBaseURL, plus the explanatory comment about the shared database), the DotWatcherStaging* keys in Info.plist, and the DOTWATCHER_STAGING_* build settings in the project file. Keep the Debug (localhost) settings. Ship a TestFlight build and confirm it hits Production and shows your existing sessions. Update ios/README.md.
  8. Retire the Staging server. config tatooine
    Only after step 7 is confirmed on your phone.
    • Remove the Staging manifests and Flux Kustomizations from Tatooine-Configuration (dot-watcher-server-staging, dot-watcher-client-staging).
    • Check the paths before committing. Flux runs with prune: true, which deletes the Namespace and its PVCs when its folder goes away. That is what we want for the two Staging namespaces and not at all for the Production ones.
    • Remove the dot-watcher-staging.skelstar.io DNS record and ingress.
    • Remove the Staging entries from the Android manifest (dot-watcher-staging.skelstar.io app link) and iOS entitlements (applinks:) in a later app release, so old builds' invite links keep working until then.
    • Delete the leftover SQLite volumes in both environments once you are happy there is no rollback need.
  9. Make local the Staging environment. repo
    docker-compose.yml and appsettings.Development.json already do this, so no code change. Document it: the staging branch is integration, tested with docker compose up -d and dotnet run, and a promote PR to main is the release. Keep enforce-staging.yml.
  10. Docs and comments. repo
    Update server/README.md (Deployment section: Kraken instead of /deploy and deploy.sh; remove the "Staging and Production share one database" notes, the palette sharing sentence, and the "deploy to Production first" rule; Runtime secrets: add ConnectionString), the shared-database comments in SessionStore.cs, SessionStore.Casual.cs, SessionsController.cs and CasualMaintenanceService.cs, the header of scripts/shared-postgres.yaml, and scripts/audit-user-collisions.sh / store-palettes.sh references. Comments only. Do this last so the docs describe what is true.

5. What does not change

  • Server code and schema. It already takes one ConnectionString and creates its own schema.
  • CI. server-dotnet.yml still tests against its own Postgres container.
  • Production namespaces, hostnames, DNS and data. Nothing in Production is renamed or moved.
  • Branching. PRs still go to staging and promote to main.

6. Rollback

FailureAction
A Kraken deploy to Production misbehavesRoll back in Kraken (images only). If the release changed the schema, the older release usually still starts because changes are additive; otherwise restore the step 2 dump.
New TestFlight build misbehavesThe Staging server is still running until step 8, so install the previous build. This is why step 8 comes last.
Wrong namespace removed in step 8Re-apply the manifests from git; restore the database from the step 2 dump if Postgres's namespace was touched. The Postgres instance lives in its own namespace (dot-watcher-db) and is not pruned by the dot-watcher Kustomizations.

7. Risks and open items

  • No staging means releases are tested only locally. The local setup runs the server and web client, not real-device GPS traffic or the cluster network. Kraken shows its "nothing was tested first" warning on every deploy.
  • TestFlight is now real data. A bad Production deploy affects your phone, as it affects everyone. Rollback in Kraken is the mitigation.
  • No backups exist (step 2 is the first). A recurring pg_dump is worth adding regardless.
  • Unknown until step 1: the live Flux Kustomization names, whether Production's manifests live in Tatooine-Configuration in a form Kraken can overlay, and how its secrets are referenced.
  • Kraken itself is not yet running for real (its checklist lists the first Tatooine session as outstanding). Steps 5 and 6 depend on that being done.
