Android Play internal uploads

How the Android Play internal GitHub Actions workflow builds and uploads the app to the Play internal testing track, how the version name and version code work, and what to do in the common situations. The Android twin of iOS TestFlight uploads.

What it does

One run, one internal testing release

Each run takes one commit and turns it into one release on the Play internal testing track. It never touches closed, open or production testing: anything beyond internal stays a button you press in Play Console.

Check outThe branch you picked (or the tagged commit), with full git history.
Work out the versionVersion name from the project (or the typed one); version code from the commit count.
Add secretsWrites local.properties (map key, upload keystore and passwords).
BuildbundleRelease, so it talks to Production, then checks the bundle is signed.
UploadTo the internal track as a completed release. Testers get it from the Play Store within minutes.
Internal builds use real data. Release builds always point at Production; there is no Staging server.
Version name and version code

Testers see "1.4.3 (981)"

Every Android build carries two numbers. People see the first; Play only cares about the second.

Version name
1.4.3

You set this. projectVersionName near the top of android/app/build.gradle.kts. A run can override it for one build with a typed version; nothing is committed.

Version code
981

Set automatically. The number of commits in the history of the commit being built (git rev-list --count HEAD), worked out by build.gradle.kts for local builds too. The same number as the iOS build of that commit.

The rule Play enforces

  • Every upload's version code must be higher than every version code uploaded before, on any track. Uploading the same commit twice gives the same code, so the second upload is refused.
  • Unlike TestFlight, a new version name doesn't reset this. Bumping 1.4.3 to 1.4.4 does not let a lower version code through.
  • The version name is free text to Play: it isn't checked, only shown.

Things that are not the version

  • android-v* tags are labels. Pushing android-v1.4.3 doesn't set anything; the workflow checks it matches projectVersionName and stops if it doesn't.
  • ios-v* tags and server releases (v1.x.y) are separate.
  • X-Api-Version is what the server uses to decide whether a phone is too old. Bump it only for changes that could break against the server.
Release bundles built in Android Studio use the same version code, so manual and workflow uploads can be mixed. The version codes before this scheme stopped at 29; the commit count is far above that, so the switch was safe.
What do I do when…

…I want testers to try the latest staging?

Run the workflow on staging. New commits mean a higher version code. Nothing to edit.

…I'm starting a new version (say 1.4.4)?

Either type 1.4.4 in the run's version box (this build only), or change projectVersionName to "1.4.4" in a normal PR and run on staging, or tag it: git tag android-v1.4.4 && git push origin android-v1.4.4.

…I want to test a feature branch?

Run the workflow on that branch; it works. But its version code is then used up, and staging can't upload until it has more commits. See branches and version codes.

…I ran it and nothing has changed since the last upload?

Same commit, same version code: the upload is refused. Make a commit first.

…I start two runs at once?

The second waits for the first to finish. It is never cancelled.

…I want it in production?

Promote the internal release in Play Console (Test and release → the release → Promote), or create a production release there. The workflow never does this.

Branches and version codes

Commit counts differ between branches

The version code is the commit count of whatever you build. With staging at 980 commits:

980
Upload from staging. accepted
983
Upload from my-feature: staging plus 3 commits. accepted
982
staging gets 2 more commits, then you upload it. 982 is lower than 983. refused
985+
Merge my-feature into staging: its commits and the merge commit now count too. accepted

If an upload is refused for this reason, merge the feature branch first, or wait until the branch you're building has more commits than the last upload. Bumping the version name doesn't help on Android.

Rule of thumb: upload from staging. Upload a feature branch only when you need testers on it, and merge it soon after.
Running it

By hand, on any branch

  1. GitHub → Actions → Android Play internal → Run workflow.
  2. Pick the branch, optionally type a version, and press Run workflow.
  3. When it finishes, the run's summary shows the version name, version code and commit that went up. A typed-version run also tags the commit android-v<version>.

The button only appears once the workflow file is on staging, the default branch.

With a tag

git tag android-v1.4.3
git push origin android-v1.4.3

The tag must match projectVersionName exactly, or the run stops before building.

From the command line

gh workflow run android-play-internal.yml --ref my-branch -f version=1.4.4
One-time setup
  1. Check Play App Signing is on. Play Console → Dot-Watcher → Protected with Play → Play Store protection → "Protect app signing key" should say Releases signed by Play. Then the keystore below is only the upload key, which Google can reset if it leaks.
  2. Make a service account. Google Cloud project dotwatcher-play (organisation skelstar-org) → enable the Google Play Android Developer API → IAM & Admin → Service Accounts → github-play-upload, no Cloud roles → Keys → Add key → JSON. The organisation blocks key creation by default (iam.disableServiceAccountKeyCreation, "secure by default"); it is overridden to Not enforced for this project only, which needs the Organisation Policy Administrator role.
  3. Invite it in Play Console. Users and permissions → Invite new users → the service account's email → App permissions → Dot-Watcher → Release to testing tracks. No account permissions. It can take a few hours to start working.
  4. Add repository secrets (GitHub → Settings → Secrets and variables → Actions):
    SecretValue
    PLAY_SERVICE_ACCOUNT_JSONThe whole JSON key file. Never commit it: the repo is public and Google disables keys it finds in public repos.
    ANDROID_UPLOAD_KEYSTORE_B64The upload .jks as base64. Mac: base64 -i dotwatcher-upload.jks | pbcopy.
    ANDROID_UPLOAD_STORE_PASSWORDRELEASE_STORE_PASSWORD from android/local.properties.
    ANDROID_UPLOAD_KEY_ALIASRELEASE_KEY_ALIAS.
    ANDROID_UPLOAD_KEY_PASSWORDRELEASE_KEY_PASSWORD.
    LINZ_API_KEYShared with the iOS workflow. Without it the build works but the map is blank (the run warns).

The keystore and local.properties are written on the runner during the run and deleted at the end.

When it fails
Where / messageMeaningFix
"Missing repository secrets: …" One of the signing or Play secrets isn't set. Add the named secrets.
"Check tag matches the project version" The tag says one version, projectVersionName another. Change projectVersionName and commit, or delete the tag and tag the right version.
Write secrets: "ANDROID_UPLOAD_KEY_ALIAS … isn't a key in this keystore" The alias secret doesn't match the keystore. (Before this check, Gradle failed with "No key with alias '***' found in keystore".) Set the secret to one of the aliases the message lists. Typing it beats pasting.
Write secrets: "Couldn't open the keystore", or Build: keystore was tampered with / password incorrect A password secret is wrong, or the base64 was cut short. Re-copy the secrets from local.properties and the .jks.
"isn't signed" The bundle built without the upload key. Check the four ANDROID_UPLOAD_* secrets.
Upload: "Version code N has already been used" That version code, or a higher one, is already on Play. See branches: merge first or wait for more commits.
Upload: "The caller does not have permission" The service account isn't invited, lacks "Release to testing tracks", or the invite hasn't taken effect yet. Check Play Console → Users and permissions; if it was just added, try again in a few hours.
Upload: "Only releases with status draft may be created on draft app" Play treats the app as a draft (never released on any track). Change status: completed to draft in the workflow, and roll the release out by hand in Play Console.
Upload: "APK signed with the wrong key" / upload certificate mismatch The keystore in the secret isn't the upload key Play knows. Use the keystore you upload with from Android Studio, or reset the upload key in Play Console.
Installed from Play, but the map is blank LINZ_API_KEY isn't set. Add the secret and run again after a new commit.
