What it does

One run, one TestFlight build

Each run takes one commit and turns it into one build in TestFlight. It never submits anything for App Store review: that stays a button you press in App Store Connect.

Check outThe branch you picked (or the tagged commit), with full git history.
Check the versionA typed version must look like 1.4.4 and not be tagged on another commit. Tag runs: the tag must match the project's version.
Add secretsWrites Secrets.xcconfig (map key) and the API key file.
ArchiveRelease configuration, so it talks to Production. Signs itself with the API key. Uses the typed version, if any.
UploadStraight to App Store Connect. Shows in TestFlight after Apple's processing (5–15 min).
TagRuns started by hand or from Kraken only: tags the built commit ios-v<version> if that tag doesn't exist yet.
TestFlight builds use real data. Release builds always point at Production; there is no Staging server.
Version and build: the two numbers

Testers see "1.4.3 (965)"

Every iOS build carries two numbers. Apple groups builds by the first and tells them apart by the second.

Version
1.4.3

You set this. In Xcode: the DotWatcher target → General → Version (it is MARKETING_VERSION in the project file). A version typed when starting the workflow overrides it for that one build; the project file is never changed.

Build
965

Set automatically. The number of commits in the history of the commit being built (git rev-list --count HEAD), stamped by the project's "Stamp Git Commit SHA and Build Number" build phase. Ignore the 864 in Info.plist: it is replaced at build time.

The rules Apple enforces

  • Each build number can be uploaded once per version, and it must be higher than the builds already uploaded for that version. Uploading the same commit twice gives the same build number, so the second upload is refused.
  • Once a version is approved for the App Store, it is closed. No more builds of 1.4.3 can be uploaded after 1.4.3 is approved; the next upload has to be 1.4.4 or higher.
  • A new version starts its builds afresh, so after a version bump any build number is fine.
  • TestFlight builds expire after 90 days.

Things that are not the version

  • ios-v* tags are labels. Pushing ios-v1.4.3 doesn't set anything; the workflow checks that it matches the project's version and stops if it doesn't. Runs started by hand or from Kraken add the tag themselves after a successful upload, so the newest ios-v* tag is the newest upload.
  • Server releases (v1.x.y tags from release.yml) have their own numbers, unrelated to the app's.
  • X-Api-Version (the apiVersion constant in LocationManager.swift) is what the server uses to decide whether a phone is too old. Bump it only for changes that could break against the server, never just because the app version changed.
Builds you archive by hand on a Mac use exactly the same numbering, so manual and workflow uploads can be mixed. The same rules apply to both.
What do I do when…

…I want testers to try the latest staging?

Run the workflow on staging. The version stays the same and the build number has gone up because there are new commits. Nothing to edit.

…I'm starting a new version (say 1.4.4)?

Quickest: run the workflow on staging (or press the button in Kraken) and type 1.4.4 as the version. Nothing is committed: the Xcode project still says 1.4.3, so builds archived on a Mac keep using 1.4.3 until you bump it.

To keep the project in step:

  1. In Xcode, change Version to 1.4.4, then commit and merge to staging.
  2. Either run the workflow on staging, or tag it: git tag ios-v1.4.4 && git push origin ios-v1.4.4.

…1.4.3 has just been approved for the App Store?

1.4.3 is now closed. Bump the version (above) before the next upload, even for a small fix.

…I want to test a feature branch?

Run the workflow on that branch; it works. But that build uses up a build number for the current version, which can block a later staging upload. See branches and build numbers below.

…I ran it and nothing has changed since the last upload?

Same commit, same build number: the upload is refused. Make a commit first (even a small one) or bump the version.

…I start two runs at once?

The second waits for the first to finish. It is never cancelled.

…I want it in the App Store?

Do that in App Store Connect: pick the build under the version, fill in what's new, and submit for review. The workflow never does this.

Branches and build numbers

Commit counts differ between branches

The build number is the commit count of whatever you build, and different branches have different counts. Here is how that can bite, with staging at 964 commits and the version at 1.4.3:

964
Upload from staging. accepted
967
Upload from my-feature: branched from staging plus 3 commits. accepted
966
staging gets 2 more commits, then you upload it. 966 is lower than 967, which is already uploaded for 1.4.3. refused
969+
Merge my-feature into staging. Its commits and the merge commit now count too, so staging is past 967 again. accepted

If an upload is refused for this reason, either merge the feature branch first (as above), wait until the branch you're building has more commits than the last upload, or bump the version: a new version accepts any build number.

Rule of thumb: upload from staging as normal. Upload a feature branch only when you need testers on it, and merge it soon after.
Running it

By hand, on any branch

  1. GitHub → Actions → iOS TestFlight → Run workflow.
  2. Pick the branch. Optionally type a version such as 1.4.4 (blank uses the project's). Leave request_id blank; Kraken sets it. Press Run workflow.
  3. When it finishes, the run's summary shows the version, build and commit that went up, and the commit is tagged ios-v<version>.

A typed version is refused before building if it isn't three numbers, or if its ios-v* tag is already on a different commit (that version was uploaded from somewhere else).

The button only appears once the workflow file is on staging, the default branch. A branch made before the workflow was added doesn't have it, so it won't run there until that branch is updated from staging.

With a tag

git tag ios-v1.4.3
git push origin ios-v1.4.3

The tag must match the project's version exactly, or the run stops before building. Tag the commit you mean to ship (usually the tip of staging).

From the command line

gh workflow run ios-testflight.yml --ref my-branch -f version=1.4.4
One-time setup
  1. Make an App Store Connect API key. App Store Connect → Users and Access → Integrations → App Store Connect API → Team Keys (not Individual Keys: those have no issuer ID and xcodebuild can't sign with them) → add a key with the Admin role. If Team Keys only shows "Request Access", the Account Holder has to accept the API terms once first. Admin is what lets the build create its own distribution certificate and profile. Download the .p8 file: Apple lets you download it once.
  2. Add repository secrets (GitHub → Settings → Secrets and variables → Actions):
    SecretValue
    ASC_KEY_IDThe key's ID, shown next to it in App Store Connect.
    ASC_ISSUER_IDThe Issuer ID at the top of the API keys page.
    ASC_KEY_P8The whole file, line breaks kept: -----BEGIN PRIVATE KEY-----, the key lines between, and -----END PRIVATE KEY-----. Open it in a text editor, select all, copy, paste.
    LINZ_API_KEYThe map key from your local Secrets.xcconfig. Without it the build still works, but the map is blank (the run warns).
  3. Merge the workflow into staging, then do a first run by hand.

The API key file is written to the runner's temporary folder during the run and deleted at the end. If the key is ever leaked, revoke it in App Store Connect and make a new one.

When it fails
Where / messageMeaningFix
"Check tag matches the project version" The tag says one version, the project another. Change Version in Xcode and commit, or delete the tag and tag the right version.
Upload: bundle version "must be higher than the previously uploaded version", or "already been used" That build number is already uploaded for this version, or a higher one is. See branches: build from a branch with more commits, merge first, or bump the version.
Upload: "must contain a higher version than that of the previously approved version" This version has been approved for the App Store and is closed. Bump the version.

"Select Xcode": no Xcode 26 GitHub's Mac machine doesn't have the Xcode this project needs (iOS 26 SDK). Change runs-on: in the workflow to a Mac image that has Xcode 26.

Nothing in the workflow ran; it is not a setup problem. Re-run jobs later, try macos-15-intel, or upload from Xcode. Apple's Macs instead of GitHub's

Not needed for now: the GitHub workflow works. If GitHub's macOS shortage keeps blocking runs, Xcode Cloud could do the same job. It's a medium change, not a rewrite.

What it gives

  • Builds on Apple's own Macs, so there's no GitHub queue.
  • 25 compute hours a month included with the developer membership (roughly 60–100 uploads).
  • Signing and the TestFlight upload are built in; the ASC_* secrets aren't needed for the build.

Setup

  1. In Xcode on the Mac: Integrate → Create Workflow. Grant Apple access to the GitHub repo, choose the Archive action and the post-action "TestFlight (internal testing only)", and start it by hand and/or on ios-v* tags.
  2. Add ios/DotWatcher/ci_scripts/ci_post_clone.sh (next to the .xcodeproj). It writes Config/Secrets.xcconfig from an Xcode Cloud secret variable LINZ_API_KEY, so the map isn't blank.
  3. On the first build, check the build number.

Catches

  • Build numbers. Xcode Cloud numbers builds itself, replacing the commit-count scheme on this page. Set its "next build number" above the last uploaded build. How it interacts with the project's build-number build phase is unchecked.
  • Kraken. The Kraken phone builds plan (.ai/plans/kraken-phone-builds.md, branch kraken-phone-builds-plan) would start builds through the App Store Connect API (ciBuildRuns) with the API key already made, instead of GitHub's. Typing a version per build is harder: Xcode Cloud workflows don't take inputs the way workflow_dispatch does.
  • This workflow would stay as a fallback or be removed.
Suggested: retry GitHub a few times first; its arm64 shortages are usually temporary. Switch if they keep recurring.
